# v0.2 设计：个性化与识别质量

> 目标：做到"越用越懂你"——专有名词、人名、行业术语随使用自动变准，并且把用户的修改留存成长期迭代的资产。
>
> 本文档基于**实测**，不是推测。所有标了「实测」的结论都跑过。

**如果只看一节，看第 9 节**：那里回答了"给 LLM 一个人设有没有用"和"中英混说为什么差"，
并给出了一个反直觉的结论——**prompt 工程解决不了这个问题，必须有确定性校验兜底**。

---

## 0. 先分清三类错误——它们的修法完全不同

用 `say` 合成了一段有标准答案的语音（`这个需求由赵天翊负责，下周同步给奇绩创坛，顺便看看 Milvus 的召回率`），跑真实流水线，得到：

```
ASR 原始：这个需求由赵天义负责，下周同步给奇迹创谈，顺便看看的召回率。
标准答案：这个需求由赵天翊负责，下周同步给奇绩创坛，顺便看看 Milvus 的召回率
```

三类错误，三条完全不同的路：

| 类型 | 例子 | 能不能后处理修 | 实测结论 |
| --- | --- | --- | --- |
| **A. 常见术语拼错** | `kuubernet` → `Kubernetes` | ✅ 能 | 现有 LLM 层**已经修对了**，不需要额外工作 |
| **B. 专有名词同音字** | `赵天义`→`赵天翊`、`奇迹创谈`→`奇绩创坛` | ✅ 能 | 注入词库后 **0/3 → 2/3** |
| **C. 术语被整个漏掉** | `Milvus` 完全没识别出来 | ❌ **不能** | 后处理只会**编造**，见下 |

### 关于 C：为什么"让 prompt 补全句子"不可行（实测）

用户原话里 `Milvus` 的位置，ASR 输出的是"看看的召回率"——**那个词根本没进文本**。任何后处理都不可能知道它存在。实测让 LLM 去补：

| prompt | 结果 | 是否编造 |
| --- | --- | --- |
| 现有 prompt | `…看看召回率。` | 没编造，但也没补 |
| 加了词库 | `…看看 **DSH Voice** 的召回率。` | ❌ **编造**（从词表里随便挑了一个） |
| 加词库 + 明文"绝不新增、宁可漏改不可错加" | `…看看 **DSH Voice** 的召回率。` | ❌ **仍然编造** |

**即使 prompt 里写死禁止，模型照样编。** 所以：

> "在 prompt 里说补全句子"这条路**不能走**。它会用模型认为合理的词去填，而不是用户真正说过的词。
> 漏掉的词只能从**音频侧**救回来。

## 1. 产品模型：一个数据闭环

Typeless 那种"越用越聪明"的本质是一条闭环：

```
        说话
         ↓
      音频 ──────────────┐
         ↓               │  留存（本地）
      ASR 识别           │
         ↓               │
      LLM 润色           │
         ↓               │
      粘贴到光标处        │
         ↓               │
   用户手动修改 ←─────────┘  ← 这一步是关键，也是最难的
         ↓
      提取 (错的, 对的) 对
         ↓
      累积 → 词库 → 下一句话就更准
```

**这条闭环的每一环现在都是断的**：音频用完就删、修改完全没被观测、词库不存在。

你提的两个需求（个性化 + 修改数据留存）其实是**同一条闭环**：留存是学习的前提，学习是留存的目的。

## 2. 五个可用杠杆（按性价比排序）

### L1｜词库注入 prompt　`实测有效，改动最小`

把用户词表拼进 `llm.mjs` 的 system prompt。

- **实测**：`0/3 → 2/3`，输入 token `258 → 305`（+47），成本可忽略
- **必须配套硬校验**：实测发现模型会编造，所以 LLM 输出里**新增**的词表词，要检查原文是否存在拼音相近的片段；没有就丢掉
- 改动位置：[sidecar/llm.mjs](sidecar/llm.mjs) 的 `SYSTEM_PROMPT` + `isPlausible`

### L2｜sherpa-onnx 原生 Homophone Replacer　`已端到端实测`

我原本打算自己写"拼音模糊替换"，**结果 sherpa-onnx 自带这个功能**。已在我们自己的环境
（`sherpa-onnx-node@1.13.8` + SenseVoice int8 + 官方测试素材）跑通：

| 配置 | 输出 |
| --- | --- |
| 不用 `hr` | 下面是一个测试**悬界芯片**，湖南人**公投安装**机载传感器。 |
| **用 `hr`** | 下面是一个测试**玄戒芯片**，湖南人**弓头安装**机载传感器。 |

用的就是本项目的 `language: "auto"` + `useInverseTextNormalization: 1`。
**零模型改动、零延迟、不联网、不编造。**

需要两个文件：`lexicon.txt`（汉字→带调拼音，从官方 `hr-files` release 拿）+
`replace.fst`（用 `pynini` 生成，规则形如 `xuan2jie4xin1pin4` → 玄戒芯片）。

> #### ⚠️ 实现时必须注意：`hr` 要放在**构造函数**里
>
> 实测（同一段音频，三次对照）：
>
> | 配置 | 结果 |
> | --- | --- |
> | 完全不用 `hr` | 基线，不纠正 |
> | **`hr` 在构造函数里**，之后照常 `setConfig` | ✅ 2/2 纠正 |
> | `hr` 只在 `setConfig` 里给（构造时没有） | ❌ **完全不纠正**，与基线一字不差 |
>
> 这对本项目尤其关键：`server.mjs` 每次解码前都会调
> `recognizer.setConfig(nativeConfigRef)`（为了切语言）。好消息是那个对象就是构造时用的同一个，
> 所以**只要把 `hr` 加进 `loadModels()` 里的 `nativeConfig` 即可**，后续 setConfig 会自然带上。

**能力边界**：`hr` 是**静态**的——官方明确说规则文件不支持运行时修改，且 `pynini` 现在基本只能在
Linux 上装。所以它适合承载**稳定的领域词表**，不适合承载"越用越学"的动态词库。
只做中文替换，非中文原样透传。

**分工**：`hr` 管稳定词表（硬、准、离线）；L1 的 prompt 注入管长尾与动态部分（软、全）；
L3 学到的词若要硬生效，走 §4.3 的 JS 拼音层。

### L3｜学习记忆　`核心，本文档第 3 节详述`

从用户的修改中提取替换对，累积成词库。**这是"越用越聪明"的本体。**

参照竞品（均据厂商文档）：Typeless 在用户改正后会把词自动加进 "Auto-added"；
Wispr Flow 与 Superwhisper 都是**软提示 + 硬替换两层并存**——提示是概率性的、替换是确定性的，
成熟产品两层都做，缺一不可。

### L4｜换用带原生热词的模型　`重，暂缓`

研究确认：SenseVoice **没有**热词能力（官方文档："只有 transducer 模型支持 hotwords"；实测传 `hotwordsFile` 会直接抛错，要求改用 `modified_beam_search`）。

但同一份绑定里有两个模型**原生支持热词**：`funasr_nano` 和 `qwen3_asr`（Qwen3-ASR-0.6B int8 约 937MB，30+ 语言，含中文方言）。

- Qwen3-ASR 是 sherpa 里唯一能同时拿到**原生热词 + 中英混说**的选项
- 但体积是 SenseVoice 的 4 倍（239MB → 937MB），内存和延迟都会涨
- **建议先不做**，等 L1+L2+L3 的效果数据出来再判断

### L5｜音频侧：解决"轻声漏字"　`实测定位到根因`

见第 4 节。这一条和个性化无关，但直接决定可用性。

## 3. 学习记忆：怎么设计

### 3.1 捕获用户修改——三个层次，建议同时做

#### (a) 自动捕获（最理想，也最脆弱）

粘贴后观测焦点输入框，检测用户改动。

```
粘贴时刻 T0：记录 (粘贴文本, 焦点 AX 元素)
T0 + 1s…30s：每 2 秒读一次该元素的 value
退出条件：焦点转移 / 窗口关闭 / 超时
diff：(粘贴文本) vs (元素当前值) → 提取修改
```

- ✅ 零打扰，这才是 Typeless 那种"不知不觉变聪明"的体验
- ⚠️ 依赖目标 App 把文本暴露给辅助功能 API。原生控件（备忘录、邮件、大部分编辑器）可以；**Electron 应用、终端、部分网页输入框读不到**
- ⚠️ **隐私升级**：App 从"读按键"变成"读输入框内容"。必须默认关闭 + 明确告知，且只在粘贴后的短窗口内观测，不做常驻监视

#### (b) 听写历史窗口（可靠兜底，也是"留存修改数据"的直接实现）

菜单栏新增「听写历史…」：列出最近的转写，用户可以在窗口里直接修订。

- ✅ 不依赖 AX 读取，任何场景都能用
- ✅ 天然就是"修改数据留存"的载体
- ✅ 用户看得见、可删除，隐私上更可控
- ⚠️ 需要用户主动去做，不如 (a) 无感

#### (c) 纠错快捷键（中间态）

菜单栏「上一条不对…」→ 弹出输入框，预填刚才的文本，用户改完回车即学习。成本低，但打扰用户。

**建议：先做 (b)，再补 (a)。** (b) 能立刻验证学习算法是否有效，(a) 只是把它变得无感。

### 3.2 从一对文本里学到什么

给定 `(raw, corrected)` 做字符级对齐，分三类：

| 模式 | 例子 | 含义 | 处理 |
| --- | --- | --- | --- |
| **同音替换** | `赵天义` → `赵天翊` | 典型同音字错误 | ✅ 高置信，直接进词库 |
| **插入** | `看看的召回率` → `看看 Milvus 的召回率` | 用户补了漏掉的词 | ⚠️ 词对词不成立，但**说明这个词该进词库**（用于 L1/L2 下次提前偏置） |
| **删除/改写** | 用户删掉了多余内容 | 口语习惯差异 | 忽略，或作为清理规则的反馈 |

关键点：**判断"是否同音"用拼音，不用字符串。** 用 `pinyin-pro`（纯 JS，无原生依赖）算拼音，允许声调不同、`zh/z`、`ch/c`、`sh/s`、前后鼻音混淆。

### 3.3 词库的形态

两个文件，职责分开：

```jsonc
// ~/.voice-global/dictionary.json —— 用户自己维护的（可以手改、可以分享）
{
  "terms": ["赵天翊", "奇绩创坛", "Milvus", "DSH Voice"],   // 用于 L1 注入 + L2 生成替换规则
  "protect": []                                            // 永远不要被清理规则删掉的词
}
```

```jsonc
// ~/.voice-global/learning.jsonl —— 系统自动积累的（一行一条，可审计、可回滚）
{"ts":"2026-09-30T23:40:12Z","wrong":"赵天义","right":"赵天翊","pinyin":"zhao4tian1yi4",
 "count":3,"first":"2026-09-28T...","last":"2026-09-30T...","sources":["ax-edit","history"],"confidence":0.92}
```

**推广策略**：`count >= 2` 且拼音匹配且长度相同 → 自动生效；否则只在历史窗口里提示用户"要不要加进词库"。

**为什么要 JSONL 而不是直接进词典**：可以审计、可以回滚、可以看出"这个词是怎么学来的"。出问题时删掉对应行即可。

### 3.4 生效路径（三级，由快到慢）

```
ASR 输出
   ↓
① Homophone Replacer（本地 FST，<1ms，确定性）   ← 已学到的同音替换
   ↓
② 词表注入 prompt（LLM 层，覆盖面最广）           ← 用户词表
   ↓
③ LLM 输出后校验（丢掉没有拼音依据的新增词）      ← 防编造
   ↓
④ 句尾标点处理
   ↓
粘贴
```

## 4. 录音与修改数据的留存

### 4.1 现状

[main.swift:207-220](Sources/main.swift#L207-L220)：写完临时 WAV → 转写 → `defer` **立刻删除**。所以机器上一条真实录音都留不下。

> 这次做实验时我不得不**用 `say` 合成语音**，就是因为没有真实数据。这就是这个功能的价值。

### 4.2 设计

开启后，把 `defer 删除` 改成 `move 到 recordings/`，并追加一条元数据：

```
~/.voice-global/recordings/
  index.jsonl              ← 一行一条，可直接 jq / grep
  audio/2026-09-30T23-40-12-345Z.wav
```

`index.jsonl` 每条记录：

```jsonc
{
  "ts": "2026-09-30T23:40:12.345Z",
  "audio": "audio/2026-09-30T23-40-12-345Z.wav",
  "seconds": 3.17,
  "text": {
    "raw": "这个需求由赵天义负责…",      // ASR 原始
    "rules": "这个需求由赵天义负责…",    // 规则层
    "final": "这个需求由赵天翊负责…"     // 实际粘贴出去的
  },
  "hits": ["filler:呃", "llm"],
  "timings": { "asr": 190, "cleanup": 1, "llm": 559 },
  "usage": { "prompt_tokens": 305, "completion_tokens": 26 },
  "finalText": "…",                       // 用户后来改成什么样（学习闭环写回这里）
  "env": { "language": "auto", "cleanup": "llm", "model": "sensevoice-int8", "appVersion": "0.2.0" }
}
```

**`env` 那一段是关键**：记录了当时的模型、参数、版本。将来改了 VAD 阈值或换了模型，可以拿这批音频做**离线 A/B**，直接量出"改动到底有没有让识别变准"。

### 4.3 隐私与容量（必须一起设计）

| 问题 | 方案 |
| --- | --- |
| 隐私 | **默认关闭**。开启时明确提示"录音只存在本机，不会上传"。README 和首次启动都要写清楚 |
| 容量 | 16kHz/16bit 单声道 = **32KB/秒**。一天 100 次 × 10 秒 ≈ 32MB/天 ≈ 1GB/月 |
| 保留策略 | 三个上限任选：最多 N 条（默认 500）/ 最多 XXX MB（默认 500MB）/ 最多 N 天（默认 30 天），超出删最旧 |
| 排除备份 | 建议放 `~/.voice-global/recordings/`，并提示用户可用 Time Machine 排除规则 |
| 一键清空 | 菜单里给「清空录音与学习记录」 |

### 4.4 为什么这套东西能反哺长期迭代

1. **评测集**：改 VAD 阈值、换模型、调 prompt，都能拿同一批真实音频跑回归，而不是靠感觉
2. **学习素材**：`(音频, raw, final)` 三元组是训练/调参的原料
3. **回归测试**：把典型错误固化进测试，防止改 A 坏 B
4. **判断 L4 值不值得做**：有了真实数据才能回答"换 Qwen3-ASR 到底提升多少"

## 5. 轻声漏字：根因与修法

### 5.1 实测定位

把合成语音按不同衰减跑同一套流水线：

| 电平 | 识别结果 | 变化 |
| --- | --- | --- |
| 正常（-2.6 dBFS） | `我们用kuubernet部署了微服务架构…` | 基准 |
| -14.6 dBFS | `ubernet部署了微服务架构…` | ❌ 开头"我们用"丢了 |
| -22.6 dBFS | `ubernetes部署了微服务架构…` | ❌ 仍然丢 |
| -28.6 dBFS | `ubbernet部署了微服务架构…` | ❌ 仍然丢 |
| -22.6 dBFS 后**归一化**回去 | `们用kuubernetes部署了…` | ✅ **部分恢复** |

### 5.2 根因（读代码定位）

1. [Recorder.swift](Sources/Recorder.swift) **全程没有任何增益或归一化**，只是 `clamp` 到 [-1, 1]
2. [server.mjs:81](sidecar/server.mjs#L81) 的 Silero VAD `threshold: 0.5` —— 轻声段落的语音概率低于 0.5，**不被判为语音 → 整段丢失**
3. 只有"VAD 完全没切出内容"时才有整段兜底解码（[server.mjs:158](sidecar/server.mjs#L158)）。**部分漏检就静默丢字**——这正是你遇到的情况

### 5.3 修法（按优先级）

1. **解码前做增益归一化**（实测有效）：在 `readWav` 之后、VAD 之前，按 RMS 归一化到目标电平，带峰值上限保护。改动约 15 行
2. **VAD 参数放宽**：`threshold` 0.5 → 0.3，`minSpeechDuration` 0.25 → 0.1
3. **HUD 提示音量过低**：用户能自己纠正（离麦克风近一点）
4. `AVAudioEngine` 开 voice processing（AGC）：能自动增益，但会改变音频特征，**需要实测是否影响识别**

> ⚠️ 注意 1 和 2 都要**用第 4 节的录音语料做回归**，不能凭感觉调——VAD 阈值降低会引入更多噪声幻觉。

## 6. 句尾不留标点

最简单的一条：在**最终输出**剥掉末尾的 `。！？.!?…；;`。

关键细节：
- 必须在 **LLM 之后**执行——LLM 会自己补句号
- 只剥**整段最后**一个，中间的句号保留
- 规则层单独用时也要生效

**需要你定一个边界**：问句的 `？` 要不要也去掉？去掉会丢失疑问语气（"你明天来吗" 显得像陈述）。两个选项：

- 全部剥掉（完全按你说的"留空"）
- 只剥 `。！` 和英文 `.`，保留 `？`

## 7. 建议的实施顺序

| 阶段 | 内容 | 为什么先做 |
| --- | --- | --- |
| **P0** | 录音留存 + `index.jsonl` | **其它一切都依赖它**。没有真实数据，后面每改一处都只能靠感觉 |
| **P1** | 句尾标点（需求 3） | 一行改动，立刻可用 |
| **P2** | 增益归一化 + VAD 放宽（需求 2） | 拿 P0 的语料做前后对比，能直接量出改善 |
| **P3** | 词库 + L1 注入 + 防编造校验 | 实测 0/3 → 2/3，性价比最高 |
| **P4** | 听写历史窗口 + 学习算法（L3） | 个性化闭环成型，开始"越用越聪明" |
| **P5** | Homophone Replacer（L2） | 让学到的替换变成本地确定性规则，省 LLM 调用 |
| **P6** | AX 自动捕获修改 | 把 P4 变成无感 |
| 待定 | 换 Qwen3-ASR（L4） | 等 P0 的数据说话 |

## 8. 待确认的风险

1. **AX 读取输入框内容**能不能在目标 App 上稳定工作——需要实测主流 App（微信、飞书、浏览器、VS Code、终端）
2. **同音误伤**：拼音匹配会不会把本来正确的词改错，需要构造对抗用例
3. **pynini 生成 FST** 的可复现性（用户机器不需要 pynini，但我们生成时需要）
4. **录音的功能许可**：留存用户录音涉及隐私，需要明确的开启流程和说明文案
5. 中文 transducer 替代模型、以及 Typeless / Wispr Flow 的具体个性化机制，研究仍在进行中

## 9. 补充实验：人设、中英混说，以及 prompt 的边界

这一节的结论来自三组受控实验。**它推翻了"调 prompt 就能解决"的直觉。**

### 9.1 中英混说差在哪：不是"混杂"，是英文词汇量

用 `say` 合成，逐句用**纯 ASR（绕过 VAD）**解码，排除 VAD 干扰：

| 测试句 | 标准答案 | ASR 输出 |
| --- | --- | --- |
| 纯英文句 | `Milvus is a vector database…` | `**Mvis** is a vector database…` |
| 中文里嵌 | 我们用 **Milvus** 做向量检索 | 我们用 **mvis** 做向量检索 |
| 中文里嵌 | 我们用 **Pinecone** 做向量检索 | 我们用 **piniccom** 做向量检索 |
| 高密度英文 | 把代码 **deploy** 到 **staging** 环境跑一下 **regression test** | 把代码 **de** 移到 **stging** 环境跑一下 **regression test** |

**`Milvus` 在纯英文句子里也拼错** —— 所以问题不是"中英切换"，是 SenseVoice 的英文词表覆盖不够。
中文部分几乎不出错（`张天然`、`微服务架构` 都对）。

**`language` 参数（auto / zh / en / yue）对混说几乎没有影响**：4 个设置命中率都在 2/3 左右，
`yue` 反而更差。调这个参数没有收益。

### 9.2 `useInverseTextNormalization` 是一个权衡，不是纯收益

| 配置 | `Kubernetes` | `OKR` | `三点` |
| --- | --- | --- | --- |
| `itn=1`（现状） | `kuubernetes` ❌ | `OKR` ✅ | `3点` ✅ |
| `itn=0` | `kubernetes` ✅ | `o k r` ❌ | `三点` |

**没有两全的设置。** 保持 `itn=1`，把英文拼写交给后处理层修，是更划算的选择
（缩写被拆成 `o k r` 是后处理救不回来的）。

### 9.3 人设有没有用：有用，但不稳定

四个变体，同一批用例，`temperature=0`：

| 变体 | 正确率 | 平均输入 token |
| --- | --- | --- |
| A 现状（无注入） | **1/4** | 239 |
| B 只加词表 | **3/4** | 282 |
| C 人设 + 词表 | **4/4** | 392 |

看起来"人设"赢了。但换一批用例（加了编造金丝雀）再跑：

| 变体 | 正确率 | 失败方式 |
| --- | --- | --- |
| D 词表 + 中英混说指令（无人设） | 4/5 | 英文保住了，但**编造了 `DeepSeek`** |
| E 人设 + 词表 + 防编造铁律 | 4/5 | 不编造了，但**把 `deploy` 翻译成了"部署"** |

**D 和 E 失败在相反的方向。** 加"防编造"规则会把"保持英文"规则挤掉，反之亦然。

> **结论：prompt 的指令容量已经饱和了。** 靠堆规则在几个失败模式之间来回搬运，
> 不能同时消除。这不是提示词写得不够好，是这条路的天花板。

### 9.4 所以正确的架构是：prompt 尽力 + 确定性校验兜底

后处理层要做三件事，其中第三件是新增的：

1. **词表注入**（最大杠杆，实测 1/4 → 3/4）
2. **指令**：明确写"用户夹的英文必须保持英文，不要翻译"——单独这条实测有效
3. **输出校验（新增，关键）**：把 LLM 输出与 ASR 原始文本做**对齐**，然后：

   | 情况 | 判定 | 处理 |
   | --- | --- | --- |
   | 输出里的词能在原文找到对应（哪怕是拼坏的形式，如 `mve` → `Milvus`） | **替换** | 接受 |
   | 输出里凭空多出原文完全没有对应位置的词 | **插入** | **撤销**，判为编造 |
   | 原文里的英文词被换成了中文 | **翻译** | **撤销**，恢复英文 |

   判定用**对齐**而不是相似度：`mve` 和 `Milvus` 的相似度很低，但它们在句中的位置是对应的；
   而 `DeepSeek` 在原文里连位置都没有。这个区分相似度做不了，对齐可以。

   实测对照：`mve → Milvus` 是替换（该留），`的召回率 → DeepSeek 的召回率` 是插入（该撤）。

### 9.5 一个无法绕过的限制

当英文词被**整个丢掉**（原文里连残片都没有），后处理永远救不回来。实测：

```
标准答案：…顺便看看 Milvus 的召回率
ASR 输出：…顺便看看的召回率。        ← 那个位置是空的
```

让 LLM 去补，它会**编造**（实测填过 `DSH Voice`、`DeepSeek`、`recall`），
而且**即使 prompt 里明文禁止"绝不新增"，照样编造**。

**这类错误只能从 ASR 侧解决**：SenseVoice 不支持热词（见 §2 L4），
要真正的上下文偏置就得换 `qwen3_asr` 或 `funasr_nano`。这是 P6 阶段用录音语料去回答的问题——
**先量出"被丢掉"占所有英文错误的几成，再决定值不值得换一个 4 倍大的模型。**
